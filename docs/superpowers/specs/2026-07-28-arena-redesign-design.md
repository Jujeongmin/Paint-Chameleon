# 아레나 재설계 (2026-07-28)

> **후기 (2026-07-29) — 섹션 2(미미크리)는 구현 후 폐기됐다.**
>
> 관문(드럼 구역, Task 5)은 **통과했다** — 사용자가 직접 화면에서 확인했다. 그럼에도
> 사용자가 "코드로 만든 박스처럼 보인다"며 프리미티브 대신 에셋 모델(Kenney 킷)을
> 요구했고, 텍스처를 입힌 모델은 단색 페인트로 흉내낼 수 없으므로("드럼통에 텍스처를
> 입히면 그건 아무도 흉내 낼 수 없는 드럼통이 된다") 미미크리 자체를 버렸다. 위장은
> 이제 사물인 척하기가 아니라 **엄폐와 시야 차단**에서 나온다.
>
> **살아남은 것**: 손설계 배치, 무리마다 의도적으로 비워둔 빈 슬롯, 풍차 배치의 칸막이,
> `check:map`. 넷 다 폐기되지 않았다 — 근거만 미미크리에서 엄폐·시야 차단으로 바뀌었다.
> 이 문서를 읽는 사람은 섹션 2 이하가 여전히 유효한 설계인 것으로 오해하지 말 것.
> 실제 구현은 `docs/superpowers/plans/2026-07-28-arena-redesign.md`와 커밋
> `ba2aa4e`(에셋 모델 도입)·`4c29bb6`(88×88로 확장)를 따른다.

## 문제

현재 아레나는 프로토타입입니다. `buildMap()`이 색 클러스터 7개 안에 상자 49개를
시드 난수로 흩뿌립니다. 사용자가 지목한 두 가지 문제:

1. **숨을 곳이 설계되지 않았습니다.** 상자가 흩뿌려져 있을 뿐이라 "여기 숨으면
   좋겠다" 싶은 지점이 없습니다. 은신처가 설계의 산물이 아니라 우연의 산물입니다.
2. **보기에 성의가 없습니다.** 회색 바닥에 색상한 박스만 떠 있어 "창고"로 읽히지
   않고, 랜드마크가 없어 길을 찾을 수 없습니다.

더 깊은 진단이 하나 있습니다. 이 게임의 고유 메커닉은 **몸을 칠하고 자세를
잡는 것**인데, 현재 맵은 그걸 전혀 받쳐주지 않습니다. 상자 뒤로 몸을 가리는 것
말고는 페인팅이 쓰일 데가 없어서, 핵심 메커닉이 사실상 장식입니다.

## 결정

사용자와 합의한 방향:

- **고정 손설계 맵 하나.** 매 라운드 동일. 숨바꼭질은 "맵을 아는 것"이 곧 실력이라
  고정 맵이 깊이를 만듭니다. 서버 복제도 가장 단순해집니다.
- **숨기 = 사물인 척하기(미미크리).** 똑같이 생긴 사물 무리에 섞여 서는 것이
  "잘 숨었다"의 정의입니다. 시야 차단은 보조 수단.
- **아바타 체형은 현행 유지.** 4종의 판정 크기 동일 불변식은 이미 `check:bodies`로
  강제되고 상점 전체가 그 위에 얹혀 있습니다. 재미의 병목은 아바타가 아니라 맵입니다.

검토했다가 버린 대안:

- **구조 우선(방·복도) 접근** — 추격전은 살아나지만 미미크리가 약해지고 페인팅이
  다시 장식이 됩니다.
- **엔진 확장(원통·경사 프리미티브)** — 비주얼은 낫지만 충돌 판정을 클라·서버
  양쪽에서 고쳐야 하고, `MapBox` 하나로 렌더·충돌·스폰이 전부 도는 현재의 단순함을
  잃습니다. 과합니다.

## 섹션 1 — 구조

아레나 44×44 유지. 대각선 62u를 6u/s로 약 10초에 횡단하므로 술래 90초에 맞습니다.
크기는 문제가 아니고 **뻥 뚫린 것**이 문제입니다.

**4구역 + 중앙 교차로.** 구역마다 사물 패밀리 하나와 팔레트 하나를 전담합니다.

```
        z=-22 ───────────────────────────
              │  드럼통      ▓▓▓  팔레트  │
              │  (-12,-12)   ▓          │
              │  ═══════════ ▓          │     ▓ ═ = 칸막이
        z=-6  │              ▓          │
              │                          │
        z=0   │        중앙 교차로        │
              │        (콘크리트)         │
        z=6   │          ▓  ═══════════  │
              │          ▓   (12,12)     │
              │  화물상자 ▓    선반기둥    │
        z=22  ───────────────────────────
                x=-22        x=0      x=22
```

**칸막이는 풍차(pinwheel) 배치.** 4장을 회전대칭으로 놓아 각 구역이 중앙에서 오는
시선에 대해 가려지게 합니다. 높이 2.4 / 두께 0.6.

2.4를 고른 근거: 점프 도달 1.24 + 계단 0.45 = **1.69**이므로 올라탈 수 없고,
`CAMERA.eyeHeight` 1.5보다 높아 서서 넘어다볼 수 없습니다.

각 칸막이는 **가운데를 약 6u 비웁니다.** 끝을 비우면 빙 도는 미로가 되어 추격이
답답해집니다. 가운데 통로면 직진 진입은 되면서 시선은 끊깁니다.

이 배치가 만드는 **증명 가능한 속성**:

> 중앙 교차로에서 네 구역 중심으로 향하는 시선이 모두 막힌다.

술래는 한자리에서 훑을 수 없고 구역마다 직접 들어가야 합니다. 눈으로 확인할 필요
없이 레이캐스트로 자동 검증합니다. 칸막이 좌표를 나중에 조정해도 이 속성이 깨지면
검사가 잡습니다.

정확한 칸막이 좌표는 구현 단계에서 확정합니다. 이 문서가 고정하는 것은 배치
방식(풍차·가운데 통로·높이 2.4)과 위 속성입니다.

## 섹션 2 — 사물 패밀리

각 패밀리는 **포즈 하나의 실루엣에 치수를 맞춘 박스**입니다.

| 패밀리 | 포즈 | 박스 (W×H×D) | 이동 판정 |
|---|---|---|---|
| 드럼통 | 서기 | 0.9 × **1.86** × 0.9 | 올라탈 수 없음 (>1.69) |
| 화물상자 | 앉기 | 1.2 × 1.2 × 1.2 | 점프로 올라감 |
| 팔레트 | 눕기 | 1.8 × **0.4** × 1.8 | 걸어서 넘어감 (≤0.45) |
| 선반기둥 | 만세 | 0.6 × 2.3 × 0.6 | 올라탈 수 없음 |

드럼통 1.86은 `TOP_Y`와 **정확히 같은 값**입니다. 폭 0.9는 `maxHalfWidth` 상한의
두 배 — 어떤 체형도 드럼통보다 넓지 않습니다.

**치수의 신뢰도가 균일하지 않습니다.** 서기 실루엣(1.86 × 0.9)은 `bodies.ts`에서
정확히 나옵니다. 그러나 눕기·앉기·만세의 실제 바운딩 박스는 `Humanoid.tsx`의 리깅
수학 안에서만 나오고, 위 표의 1.2 / 0.4 / 2.3은 **어림값**입니다. 어림값으로
미미크리를 만들면 "비슷한데 미묘하게 다른" 사물이 되어 오히려 더 눈에 띕니다.

그래서 **`poseSilhouette(profile, pose)` 순수 함수를 추출합니다.** 포즈별 바운딩
박스를 계산하는 작은 모듈이고, 이것으로

- 패밀리 치수를 측정값에서 파생시키고
- `check:map`이 "모든 패밀리 박스가 대응 포즈 실루엣과 오차 내 일치"를 강제합니다

`bodies.ts`가 키·발높이를 저장 대신 파생시킨 것과 같은 수법입니다. 미미크리가 감이
아니라 검사 가능한 성질이 됩니다.

### 팔레트(색)

기존 클러스터 색을 구역별로 재배치합니다. 스포이드로 뽑을 표면이 유지됩니다.

- 드럼통 — 녹슨 주황 `0xc75b39` / `0xe08a5f`
- 팔레트 — 노랑 `0xd4a53f` / `0xe8c66b`
- 화물상자 — 보라 `0x6b4e9e` / `0x9179c4`
- 선반기둥 — 청록 `0x2f8f8a` / `0x49b3ad`
- 칸막이·중앙·벽 — 콘크리트 `0x7a7d85` / `0xb0b3ba`

**패밀리마다 색이 2종인 것이 설계 의도입니다.** 전부 같은 색이면 하이더의 페인트가
조금만 어긋나도 즉시 튑니다. 두 톤이 섞여 있으면 술래 눈에 이미 편차가 있어서
어설픈 칠도 통합니다. 위장에 관용을 주는 장치입니다.

### 빈 슬롯 — "설계된 숨을 곳"의 정의

> 패밀리 무리마다 플레이어 크기의 빈 자리를 최소 1개 의도적으로 남긴다.

드럼통은 1.5 간격으로 세우되 한 자리를 비웁니다. 박스 사이 간격(0.6)에는
플레이어(지름 0.9)가 들어갈 수 없습니다 — 의도한 바입니다. 비워둔 슬롯만이 들어갈
수 있는 자리이고, 그것이 곧 설계된 은신처입니다.

### 규모

구역당 무리 3개 × 사물 5~8개 ≈ 20개, 4구역 80개 + 칸막이 8 + 벽 4 ≈ **92개**
(현재 53개).

## 섹션 3 — 코드 구조

### 서버가 맵을 쓰는 곳은 스폰뿐

```
server.ts:98,329  randomSpawn()
  └─ rules.ts:141 randomSpawn() → isOpen() → MAP_BOXES 스캔
```

이동 검증은 직전 위치 대비 거리 clamp라 박스를 보지 않습니다. 태그 판정도 마찬가지.
즉 **박스를 통째로 복제하는 이유가 "빈자리 찾기" 하나뿐**입니다. 지금은 절차적
생성이라 함수 하나 복사로 끝나지만, 손설계 맵을 복제하면 박스 92개 리터럴을 양쪽에
두게 됩니다. 최악의 방향입니다.

### 스폰 지점도 손으로 정합니다

```ts
export const SPAWN_POINTS: [number, number][] = [ /* 12~16개 */ ];
```

서버는 이 짧은 목록만 알면 되므로 **`CLUSTERS` / `buildMap` / `MAP_BOXES` /
`isOpen`을 서버에서 전부 삭제**합니다. 이 프로젝트에서 가장 큰 중복이 사라집니다.

부수 이득: 랜덤 스폰은 "빈자리인가"만 보장하지만, 손으로 고른 지점은 **의도된 은신
슬롯 위에 스폰되지 않는 것**까지 보장합니다. 현재는 운이 나쁘면 최고의 은신처에
그냥 서서 시작합니다.

술래는 현행대로 `[0,0,0]` 중앙 고정. 풍차 배치와 맞물려 술래는 교차로에서 시작해
네 구역을 직접 돌아야 합니다.

### 클라이언트 파일 분리

`map.ts`가 지금 맵 내용과 충돌 판정 두 가지를 합니다. 내용이 92개로 늘면 더
섞입니다. 한 방향으로만 의존하게 나눕니다 (순환 없음):

- **`src/game/arena.ts` (신규)** — `MapBox`, `ARENA`, 색상, 구역·패밀리 테이블,
  `buildArena()`, `MAP_BOXES`, `SPAWN_POINTS`. 충돌 로직 없음.
- **`src/game/map.ts`** — `STEP_HEIGHT`, `groundHeightAt`, `playerBlockedAt`,
  `moveXZ`, `resolveMove`. `arena.ts`를 import하고 기존 이름을 그대로 re-export하므로
  **다른 파일은 변경되지 않습니다.**

### 검증

`check:sync`는 계약이 작아집니다 — 박스 92개 대조 대신 `SPAWN_POINTS` 대조 + 기존
`POSE_COUNT` / 속도 상한 / `AVATAR_PRICES`.

**`check:map` (신규)**:

- 패밀리 박스가 대응 포즈 실루엣과 오차 내 일치
- 무리마다 빈 슬롯 ≥1개 — 비어 있고, 스폰에서 실제 물리로 도달 가능하고, 같은
  패밀리 사물 2개 이상과 인접
- 중앙에서 네 구역 중심으로의 시선이 모두 막힘
- 스폰 지점 전부 빈자리이고 도달 가능
- 칸막이·드럼통·기둥은 올라탈 수 없고(>1.69), 팔레트는 걸어 넘어감(≤0.45)

**기존 검사 수정 예정**: `check:movement`의 *"가장 낮은 아레나 상자는 걸어 올라갈
수 없다"* 는 이 설계에서 실패합니다. 팔레트(0.4)가 일부러 걸어 넘어가는 물건이기
때문입니다. 패밀리별 기대값으로 다시 씁니다.

## 섹션 4 — 작업 순서와 위험

### 순서

1. **`poseSilhouette()` 추출** — 패밀리 치수가 여기서 파생되므로 먼저.
2. **`arena.ts` 분리** — 동작 변화 0. 기존 검사가 그대로 통과하는 것으로 검증.
   이후 작업이 제자리에 떨어지도록 일찍.
3. **`check:map` 작성** — 배치보다 **먼저**. 불변식이 "완성"의 정의이므로, 검사를
   먼저 쓰고 통과할 때까지 배치를 조정합니다.
4. **드럼통 구역 하나만 배치 → 브라우저에서 눈으로 확인** ← 관문. R2 참고.
5. 나머지 3구역 + 칸막이 배치.
6. **`SPAWN_POINTS` + 서버 슬림화** — 배치가 굳은 뒤라야 스폰 지점을 정할 수 있음.
7. `check:movement` 패밀리 기대값 수정, `check:sync` 축소.

### 위험

**R1 — `poseSilhouette` 추출이 깔끔하지 않을 수 있음.**
포즈 변환은 `Humanoid.tsx`의 R3F 그룹 계층 안에서 적용됩니다. 밖에서 정확한 바운딩
박스를 구하려면 그 계층을 다시 구현해야 하고, 둘이 어긋날 여지가 생깁니다.
막히면 대안: 브라우저에서 한 번 실측해 측정값을 상수로 박고 **측정 방법을 주석에
남긴 뒤**, `check:map`은 파생값 대신 `드럼통 높이 == TOP_Y` 같은 **관계**만
강제합니다. 열화되지만 어림짐작보다 낫습니다.

**R2 — 미미크리가 통하지 않을 수 있음. 가장 큰 위험.**
설계 전체가 "칠하고 자세 잡은 사람이 멀리서 사물로 보인다"에 걸려 있는데 그것이
한 번도 확인된 적이 없습니다. 그냥 사람으로 보일 가능성이 실재합니다.

그래서 4번을 관문으로 둡니다. **실루엣을 정확히 아는 드럼통 구역 하나만 만들고,
브라우저에서 확인하고, 통하면 나머지를 진행합니다.** 92개를 다 만든 뒤에 실패를
알면 전부 버려야 합니다.

관문에서 실패하면 설계 방향을 다시 잡습니다 — 섹션 2를 버리고 "구조 우선(방·복도)"
접근으로 선회하는 것이 준비된 후퇴로입니다.

**R3 — 서버 스폰 변경이 매칭 경로를 건드림.**
`isOpen` / `MAP_BOXES` 삭제가 예상 못 한 곳을 깨뜨릴 수 있습니다. 단계마다 서버
테스트 22개를 돌립니다.

**R4 — 박스 92개 = 메시 92개** (현재 53개). 아마 괜찮지만 측정합니다. 문제면
인스턴싱.
