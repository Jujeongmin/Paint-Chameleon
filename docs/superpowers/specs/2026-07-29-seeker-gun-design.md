# 술래의 총 (2026-07-29)

## 문제

술래가 하이더를 잡는 방법이 **밀착 후 클릭**입니다. `requestTag`가 거리 2.6u 이내 +
시선 dot 0.55 이상을 요구하고(`server/src/server.ts`), 클라이언트는 캔버스 클릭 중
"거의 움직이지 않은 클릭"만 태그로 셉니다(`src/game/LocalPlayer.tsx`).

그런데 아레나가 이번 세션에 44×44 → 88×88로 넓어지고 박스가 53 → 621개가 됐습니다.
술래는 90초 안에 대각선 124u짜리 맵을 뒤져 하이더에게 **2.6u까지 붙어야** 합니다. 추격이
길어지고, 찾는 것과 잡는 것이 별개의 노동이 됐습니다.

사용자 요청: 술래가 총을 들고 쏴서 맞추는 방식으로 바꿉니다.

## 결정

질문으로 확정한 것:

- **무제한 사거리 히트스캔.** 보이면 맞습니다. 안개가 55~135u에서 걷히므로 사실상 안개가
  사거리 상한 역할을 합니다(대각선 124u).
- **벽이 막습니다.** 엄폐물 뒤는 안전합니다.
- **시야 판정은 클라이언트, 서버는 거리를 안 봅니다.**
- **한 발에 잡힙니다.** 체력도, 페인트 마킹도 없습니다.
- **제한은 쿨다운 700ms만.** 탄수·장전 없음.
- **총소리는 하이더에게도 들립니다 — 거리만큼 작게.**
- **근접 태그는 없어집니다.** 잡는 방법은 사격 하나입니다.
- **총 모델은 Kenney Blaster Kit** (CC0). 맵이 이미 Kenney Factory·Survival·City라 같은
  작가의 컬러맵 스타일이 맞습니다. 다른 팩을 섞으면 총만 이질적으로 보입니다.

검토했다가 버린 대안:

- **연출만 (사거리 2.6 유지)** — 제일 싸지만 "총인데 2.6m"가 이상합니다.
- **서버에 맵을 다시 준다** — 정직하지만 이번 세션에 지운 박스 621개 중복이 부활하고,
  산개물이 시드 난수라 생성기까지 서버로 복사해야 합니다.
- **서버가 큰 엄폐물만 안다** (칸막이·건물·사물 열) — 중복이 가벼우면서 벽 판정을 서버가
  하지만, 작은 엄폐물 뒤는 서버가 몰라 통과시킵니다. 부분적인 안전은 안전보다 나쁩니다 —
  어디가 안전한지 플레이어가 알 수 없습니다.

## 섹션 1 — 이 변경이 버리는 것

**`TAG.maxDistance` 2.6이 사라지면 "가짜 태그 요청"의 상한도 사라집니다.**

지금 조작된 클라이언트가 할 수 있는 최대는 2.6u 안의 누군가를 잡았다고 주장하는 것입니다.
사거리가 무제한이 되면 서버에 남는 검사는 페이즈·역할·대상 유효성·쿨다운·시선뿐이고,
**맵 어디의 누구든 이름만 알면 잡았다고 주장할 수 있습니다.** 시선 검사가 "적어도 그쪽을
보고는 있어야 한다"를 요구하지만, 대상의 위치 자체가 클라이언트 보고값입니다.

이건 무제한 사거리를 택한 대가입니다. **서버가 맵을 모르는 한 되찾을 방법이 없습니다** —
벽 판정을 서버가 못 하니 "여기서 저기가 보이는가"를 서버가 판단할 수 없고, 따라서 어떤
거리 상한도 임의값입니다.

이 프로젝트는 이미 "클라이언트가 자기 위치를 소유한다"를 README 알려진 한계에 적어두고
있어 노선이 어긋나지는 않습니다. 이 항목도 같은 곳에 추가합니다. **작은 글씨로 넘기지
않습니다 — 사거리 무제한을 다시 논의할 때 이 문단이 근거입니다.**

## 섹션 2 — 명중 판정은 클라이언트

`src/game/useShoot.ts` (신규). `useBrush`와 같은 구조를 씁니다 — 레이캐스터 하나, 포인터
이벤트, 매 프레임 갱신되는 `latest` ref.

발사 한 번의 절차:

1. 조준점(포인터 락 중앙, 자유 시점이면 커서)에서 카메라를 통과하는 레이를 만든다.
2. `scene.children` 전체를 `intersectObjects(…, true)`로 가장 가까운 것부터 받는다.
3. 순서대로 훑어 **처음 만난 실체**를 판정한다. 와이어프레임(자기 위치 표시용)과 보이지
   않는 메시는 건너뛴다.
4. 그게 하이더의 몸이면 **명중**, 아니면(맵 지오메트리·자기 몸·바닥) **빗나감**.

벽 판정이 여기서 공짜로 나옵니다 — 벽이 먼저 맞으면 몸에 닿지 않습니다. 별도의 시야
계산이 없습니다.

명중한 메시에서 계정을 알아내려면 몸이 자기 정체를 들고 있어야 합니다. `RemotePlayers`가
각 플레이어 그룹에 `userData.account`를 심고, `useShoot`은 맞은 메시에서 조상을 거슬러
올라가 그 값을 찾습니다. `useBrush`의 `isDescendantOf`가 이미 같은 일을 합니다.

## 섹션 3 — 서버는 결정만, 그리고 그 결정을 순수 함수로

`requestTag`가 `requestShot(targetAccount)`이 됩니다. 검사 항목:

| 검사 | 거절 사유 |
|---|---|
| 추적 페이즈인가 | `not_seeking` |
| 보낸 사람이 술래인가 | `not_seeker` |
| 대상이 존재하는가 | `missing` |
| 대상이 안 잡힌 하이더인가 | `invalid_target` |
| 쿨다운 700ms 지났는가 | `cooldown` |
| 술래가 대상 쪽을 보는가 | `not_facing` |

거리 검사만 사라지고 나머지는 그대로입니다.

**이 결정표를 `server/src/rules.ts`의 순수 함수로 뽑습니다** —
`canShoot(o): { ok: true } | { ok: false; reason: ShotFailure }`. 서버 파일에는 상태를
읽어 넘기는 배선만 남습니다.

이유는 스타일이 아니라 검증 가능성입니다. `@agent8/gameserver-node` 테스트 하네스는
라운드를 페이즈 전환까지 못 돌립니다(리더보드·코인 적립·셀 순간이동이 모두 같은 벽에
막혀 있습니다). 결정이 `server.ts` 안에 인라인으로 있으면 **거절 사유 여섯 개 중 하나도
검증할 수 없습니다.** 순수 함수로 나오면 `check:shot`이 전부 덮습니다. `applyPurchase`가
이미 같은 이유로 그렇게 되어 있습니다.

## 섹션 4 — 총 렌더

`Humanoid`에 `held?: ReactNode` 슬롯을 추가하고 오른쪽 어깨 그룹 안에 렌더합니다.
`shoulderR`은 이미 팔 회전(포즈·걷기·점프)을 받는 그룹이므로 총이 손을 따라갑니다.

술래에게만, 추적 페이즈에만 붙습니다. 숨기 페이즈의 술래는 지하 셀에 있고 총이 없습니다.

`src/game/Gun.tsx` (신규) — Blaster Kit GLB 하나를 `useLoader(GLTFLoader)`로 읽어
손 크기에 맞춰 균일 스케일합니다. `props.tsx`의 `placeModel`과 같은 방식이고, **킷마다
자기 `Textures/colormap.png`를 상대참조하므로 `public/models/blaster/`로 따로 둡니다** —
한 폴더에 섞으면 나중 킷이 앞 킷 팔레트를 덮어씁니다.

## 섹션 5 — 피드백

**트레이서.** 총구에서 명중점(빗나가면 레이 상의 먼 점)까지 선 하나, 약 80ms. 빗나갔을
때 어디로 갔는지 보이지 않으면 조준을 배울 수 없습니다.

**머즐 플래시.** 총구에 짧은 발광 하나, 트레이서와 같은 수명.

**발사음, 거리 감쇠.** `src/audio/sound.ts`는 오실레이터 합성이고 위치 개념이 없으므로,
감쇠는 gain 계산입니다. `shotGainFor(distance)`를 **순수 함수로** 두고 `check:audio`가
덮습니다(`shouldPlayBrushTick`이 이미 같은 이유로 순수합니다).

발사는 방 전체에 브로드캐스트합니다. 각 클라이언트가 자기와 발사 지점의 거리로 gain을
정하므로, 하이더는 **가까운 총성은 크게, 먼 총성은 희미하게** 듣습니다. 사거리가 무제한이고
한 발에 잡히는 게임에서 이게 하이더가 가진 유일한 정보입니다.

조준점은 이미 있습니다(포인터 락 중앙 십자선).

## 섹션 6 — 없어지는 것

- `TAG.maxDistance`와 서버의 거리 검사
- `LocalPlayer`의 클릭-태그 핸들러(움직임 6px 이하만 태그로 세던 로직). 발사는 드리프트를
  볼 이유가 없습니다 — 자유 시점에서 시점을 끌면서 쏘는 건 정상 행동입니다.
- `onTag` 배선은 `onShoot`으로 이름이 바뀝니다

## 섹션 7 — 검증

**`check:shot` (신규)** — `canShoot` 결정표. 거절 사유 여섯 개 각각이 발생하는 케이스와,
전부 만족했을 때 통과하는 케이스.

**`check:audio` 확장** — `shotGainFor`: 0 거리에서 최대, 멀어지면 단조 감소, 음수 아님,
아주 먼 거리에서 0에 수렴.

**서버 테스트** — `requestShot`이 추적 페이즈 밖에서 거절되는지. 기존
`tag is refused outside the seeking phase`를 고쳐 씁니다. 그 이상은 하네스가 못 갑니다.

**화면 확인** — 명중·빗나감·벽 뒤 안전·트레이서·총소리 감쇠는 전부 눈과 귀로만 확인
가능합니다. 셀과 마찬가지로 **아직 아무것도 화면으로 확인되지 않았음을** 기억하십시오.

## 위험

**R1 — 무제한 사거리 + 한 발 = 하이더가 너무 불리할 수 있습니다.** 술래가 열린 곳에 서서
훑으면 됩니다. 완화책은 이미 맵에 있습니다: 풍차 칸막이가 중앙에서 네 구역으로 가는 시선을
막고(`check:map`이 강제), 산개물 440개가 시야를 끊습니다. 그래도 **플레이해봐야 압니다.
구현 후 튜닝 항목**이며 착수를 막지 않습니다. 조정할 손잡이는 사거리 상한, 쿨다운,
한 발/여러 발입니다.

**R2 — 조준이 어려울 수 있습니다.** 100u 밖의 캡슐 몸통은 화면에서 몇 픽셀입니다. 트레이서가
학습을 돕지만, 너무 어렵다면 사거리 상한이 첫 번째 손잡이입니다.

**R3 — 안티치트가 약해집니다.** 섹션 1. 설계상 감수하는 것이고 문서에 남깁니다.

**R4 — 레이캐스트 비용.** `scene.children`을 재귀로 훑는데 아레나에 모델이 621개 있습니다.
발사당 한 번이고 쿨다운이 700ms라 초당 1.4회가 상한이므로 문제없을 것으로 봅니다. 프레임이
떨어지면 후보를 좁히는 것이 대응이지만, 그건 측정 후에 합니다.

**R5 — Blaster Kit에 GLB가 없을 수 있습니다.** 페이지에 포맷이 명시되어 있지 않습니다.
없으면 OBJ 로더로 갑니다.

## 이 문서가 정하지 않는 것

- 총 모델 파일 하나의 선택과 손에서의 정확한 위치·스케일 (구현 단계, 화면으로 맞춤)
- 트레이서·머즐 플래시의 색과 두께 (구현 단계)
- `shotGainFor`의 감쇠 곡선 상수 (구현 단계, 귀로 맞춤)
- 밸런스 재조정 (R1, 플레이 후)
